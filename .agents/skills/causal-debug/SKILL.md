# Causal Debug

```text
retained trace -> first bad arrow -> non-commuting square -> minimal solve
                       ^                                      |
                       |                                      v
                next failed arrow <- cheap decisive fixture <-+
```

## Continue the investigation

- Stop a falsified arm immediately; do not stop the investigation.
- Preserve its exact counterexample, then continue from its first new failed
  arrow when the retained evidence selects a next discriminator.
- Do not ask for permission between small, reversible, already-authorized
  diagnostic and research steps.
- Stop the turn only when the trace lacks a required fact, several materially
  different explanations remain without a discriminator, the next action
  expands authority or scope, or a frozen one-shot protocol forbids another run.

## Use evidence once

Before a run, retain one lossless observation envelope containing:

- admitted input and physical incidence;
- participating links, complete paths, ownership, and lifetime;
- every candidate's drive, opportunity, threshold, executability, and cause;
- choice groups, admitted alternatives, winner, and choice warrant;
- ordered outputs by tick and phase;
- actual world effect, returned outcome, and strengthening;
- work, propagation, natural quiescence, fingerprints, and exact replay.

Use evidence in this order:

1. existing structured core trace;
2. immutable recording and exact replay;
3. pure offline projections joining existing events;
4. new causally inert instrumentation only for a genuinely absent fact.

When the trace contains choices, run `verify_choice_contract` before interpreting
them. Stop at its first violation. If it passes, treat the choice arrow as
commuting and continue to output, world effect, return, and strengthening.
A pass does not verify sensor calibration or world morphology.

When instrumentation is missing, add the complete reusable diagnostic surface,
prove traced and untraced histories equal, run once, and answer later questions
offline. Do not add a succession of narrow print statements or broad reruns.

## Draw the physical square

Use `$dev` for the category-theory and TAME modeling lenses and ordinary domain
words in code.

Draw the same failure in two paired views:

```text
physical event view                 composition view
signal ──●──▶ choice                source ──▶ intermediate
         │                             │             │
         ▼                             ▼             ▼
       effect                       witness ──▶ observed
```

- Use the Feynman-style event view to show what physically travelled, met,
  acted, changed the world, and returned over time.
- Use the commuting view to compare that physical route with the candidate,
  choice, effect, return, and learning projection.
- The first fact present on the physical route but absent or changed on the
  projected route is the first failed arrow.

1. Name the objects: physical states, junctions, paths, outputs, and outcomes.
2. Name the arrows: fire, choose, move, return, strengthen, and reuse.
3. Ask whether the observed choice is one arrow before testing composition.
4. Compose adjacent arrows and locate the first square whose two routes differ.
5. Check whether a quotient merged distinct causes, a product coupled independent
   causes, a coproduct was presented as several causes, or a witness died before
   composition.
6. Never invent an inverse for information already discarded. Preserve the
   distinguishing physical arrow at participation instead.
7. Test identity and preservation across checkpoints, learner construction,
   ownership views, batching, and observer projections when relevant.

Prefer the smallest repair that makes the square commute using existing
physical structure. Add state only when no existing live arrow can carry the
required witness, and give that state the shortest truthful lifetime.

## Run the ladder

For each proposed solve:

1. State its predicted first changed arrow and killing falsifier.
2. Run the cheapest fixture that can observe that arrow.
3. If it fails, freeze the arm and immediately redraw the square at the new
   first divergence.
4. If it passes, climb the unchanged upstream ladder before a broad benchmark.
5. Run a full embodiment or capability test only after every prerequisite arrow
   passes.
6. Use `$dev` for any repair and its behavior, regression, and wave checks.

A benchmark failure names a symptom, not a mechanism. A software test passing
proves implementation integrity, not scientific success or authority.

## Trace and video

- Treat structured trace as scientific evidence and the source of truth.
- Produce video only from a frozen trace or exact replay, after evidence is
  fixed. Never let rendering affect physical time or learner input.
- Overlay sequence, tick, phase, selected output, actual movement, contact,
  work, and the first failed arrow so a person can understand the run.
- Keep video and large recordings out of commits unless explicitly requested;
  link the generated artifact separately.
- Do not infer a causal fact from video when the structured trace does not
  contain it. Add pure instrumentation instead.

## Report in simple English

Always state:

- what physically happened;
- the first arrow that failed;
- why the previous solve did not address it;
- the next minimal solve or discriminating test;
- whether the investigation continues, genuinely blocks, or reaches a proven
  result.

Do not call an observed failure a lesson until a solve has survived. When a
solve survives, record the lesson as “what we saw” and “what solved it.”
